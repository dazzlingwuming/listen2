## 1. 这份文档的目的

这份文档用于让下一次会话直接恢复现场，不再重复六七个小时的调查、规划和重复验证。

用户对下一次执行方式的意图很明确：

1. 以最新 `main` 的电脑端功能为基准。
2. 参考原项目已有的安卓/移动端交互。
3. 先把整个安卓版的页面、入口和主要功能链一次性铺完，生成可安装 APK。
4. 先由用户和模拟器体验整体差异，再集中修正。
5. 不要再按“改一点 → 跑一次全量 CI → 写一大批证据文档”的节奏执行整个项目。

## 2. 为什么本次耗时异常

本次不是因为“安卓版本身必须开发二十小时”，而是执行方式过度工程化：

- 把“尽快做出整体可用安卓版”扩展成了 11 个阶段、58 项验收的平台重构。
- 对每个小改动都重复执行 Android 构建、APK 签名检查、六组桌面测试和前端全套测试。
- 过早建立了 Media3、Room、证据门禁、脱敏矩阵等底层能力，却没有先完成用户最需要的整体可见功能。
- 结果是底层比较稳固，但用户还拿不到一个可以整体试用、直观对比电脑版的 APK。

**下次必须修正顺序：** 先产品蓝本和可体验 APK，再集中测试与硬化。

## 3. 已经完成的工作

### 3.1 Android 工程与手机基础界面

- Android 工程可构建 Debug APK，当前产物位于 `android/app/build/outputs/apk/debug/app-debug.apk`。
- 已有手机主页、底部导航、搜索交互、迷你播放器、播放详情和队列面板的基础适配。
- 已处理安全区、48dp 触控目标、手机尺寸和部分无障碍语义。
- Android 与页面之间使用受信任、封闭的 WebMessage/RPC，没有向页面开放任意 URL、Header、Cookie 或媒体地址。

### 3.2 Media3 原生播放

- Android 已切换为单一 Media3/ExoPlayer 播放所有者，页面不再作为 Android 音频所有者。
- 已实现播放、暂停、进度、音量、静音、上一首、下一首等原生命令和状态快照。
- 已实现通知栏/系统媒体控制、熄屏后播放、音频焦点丢失处理、空闲服务释放。
- 已实现进程停止后队列、模式、历史和近似播放位置恢复。
- 已实现重复歌曲可区分的 FIFO “下一首播放”队列、重排/移除/清空、随机/循环/真实上一首历史。
- 已修正进程恢复仪器测试的假顺序问题，宿主强停→重启→恢复链路可通过。

### 3.3 Bilibili 安全请求与页面

- 已实现 Bilibili 封闭的搜索、详情、音频描述符协议和取消/超时/页面销毁边界。
- 已过滤无效推广行，有效搜索结果可保留。
- 已完成手机搜索状态、来源标识、错误/恢复操作和歌词入口的基础界面。
- 2026-08-31 最后一次冷启动实测中，搜索成功返回 5 条当前结果。

### 3.4 NetEase 与歌词底层

- Android NetEase 搜索已从旧 v1 URL 路径迁移为封闭 v2 `netease.search` RPC。
- 已定义 NetEase 搜索、目录/详情、默认音频、主歌词和手动歌词的类型、取消、错误和脱敏合同。
- Android 端错误不再默默变成“空搜索成功”。
- QQ、酷狗、酷我、咪咕和千千在没有独立证据前保持不可用，不会显示假功能。
- 已接入 NetEase 默认音频的原生解析缝，但尚无获批/已验证的真实路由，当前会诚实返回 `route-unavailable`。
- Media3 快照已含脱敏的歌词身份和原生时钟，页面按约 500ms 节奏使用原生进度，暂停/拖动/切歌/恢复会立即更新。
- 已实现 Room v2 歌词记录、v1→v2 迁移、修订冲突、偏移边界、手动来源和隐私字段检查。
- 已实现供应商无关的歌词状态、同步/纯文本/时间戳不足/不匹配/拒绝/超时/取消分类。
- 已实现手动歌词选择、清除和 0.5 秒步长偏移的原生修订确认。

## 7. 下次正确的工作策略

### 7.1 首先重建功能基线，不直接继续 11 阶段流程

1. 读取当时最新 `main`，用用户可见的界面/功能维度建立一张简单的对照表。
2. 找回或重新获取原项目已有的 Android/移动端源码，只参考手机导航、页面和交互，不照搬过时网络/安全实现。
3. 把功能分成“已可用”“已有底层但没有页面”“完全缺失”三类，不再用阶段文档数量代替用户可见进度。
4. 先确定一个“整体蓝本 APK”的范围：所有主页面和主功能入口存在；不可用的外部能力明确标注，但不阻止其他功能体验。

### 7.2 实施顺序

1. 先补齐手机导航、搜索、歌单/收藏、账号、本地音乐、缓存/下载、历史、设置、歌词和高级播放入口。
2. 优先复用最新 `main` 的共享业务逻辑，仅对 Android 需要的网络、播放、存储和系统权限做原生适配。
3. 先做一次集中构建、基本冒烟和手机截图，生成可体验 APK。
4. 由用户或模拟器完成第一轮整体差异验收。
5. 再按验收结果集中修改，最后才跑完整 CI、安全、性能和发布门禁。

### 7.3 验证节奏

- 编码期：优先跑与当前文件直接相关的快速测试。
- 蓝本成型：跑一次 Android 构建、安装和关键冒烟。
- 提交/推送前：仍必须遵守项目规则跑 `$run-local-ci`，但不应为每个几行改动拆出一个独立发布单元。
- 用户验收后：再做严格的证据、性能、脱敏和发布类检查。
